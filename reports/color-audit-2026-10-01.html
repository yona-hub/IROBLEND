IROBLEND：色名・色見本の監査

2026-10-01 · 対象：main e61ff02 · アプリ本体は変更せず、色データと計算を調査。

グラファイトの違い

アプリ #4F545BRGB 79 / 84 / 91。青成分が最大。
参考 #594E52RGB 89 / 78 / 82。赤成分が最大。

参考の辞典は「暗い赤紫系」と説明しています。両者の明るさ・彩度は近くても、灰色の色味の方向が異なります。低彩度なので、色相角だけで違いを評価せず、実際の見本も併せて比較します。

コードから確認できた原因

  1. src/data/colorPresets.ts:81 で、最初から #4F545B を手入力している。初回実装の cc26ac8 にも同じ値があり、スマホ改善で生じた変化ではない。現在の定義に出典や参照規格を保持する項目はない。
  2. src/data/virtualPigments.ts:58 の配合は graphite: { black: 2, white: .5 }。補正前の単色は #525354 でほぼ無彩色。暖色の顔料は入っていない。
  3. src/domain/colorMixing/intuitivePalette.ts:52 は顔料の単色計算を表示用HEXへ補正する。そのため、誤った色見本を基準にすると単色テストも同じ値で合格する。54色すべてで単色補正後の見本との差は今回の計算では0だったが、外部の色名定義との一致を意味しない。
  4. src/data/virtualPigments.ts:73 は白・黒カテゴリー全体の artistHue をnullにする。アイボリーやダークスレートのような色味も、複数の有彩色を混ぜる色相誘導から除外される。表示補正には色味が残るため、完全に消えるわけではないが、UIの分類と混色上の性質が結びついている。
  5. src/data/resultColorNames.ts:12 は同じ色見本を結果の色名辞書にも取り込む。色見本の変更は、結果の色名選択にも影響する。既存の保存配合は読み込み時に再計算されるので、修正時には保存色の見え方も確認する必要がある。

計算と名称判定の確認

  • 全54色の単色一致、全1,431通りの2色組み合わせを確認。無効な色、入力順の差、1:1→3:3での比率差は0。
  • 全ペアで1:1→1:5と量を変更したとき、増やした色へ近づく距離に目立つ逆行はなし（OKLab距離の許容差0.003）。
  • 各色＋白／黒の3:1→3:5で明度の目立つ逆行はなし（Lの許容差0.001）。
  • 既存の混色モデルの回帰テスト23件も合格。これらは実物の顔料との一致や、全3〜5色の組み合わせを保証する検査ではない。

別の候補として、青みのある結果が「ウォームグレーに近い色」と表示される例が3件あった。125色の辞書でOKLab距離だけから最寄りを選ぶため、明度が近い暖色名が選ばれる場合がある。

  • light-blue ＋ dim-gray → #91969C：ウォームグレーに近い色
  • white ＋ graphite → #919599：ウォームグレーに近い色
  • milk-white ＋ dark-slate → #8D9799：ウォームグレーに近い色

54色の見本と参考値

46色は同名の洋色大辞典、7色はW3CのCSS色名、ダークスレート1色は近縁のDarkSlateGrayと比較。色辞典とCSSの値は同名でも異なることがあり、数値の違いをすべて誤りとは判定しない。外部基準との差が大きい色は、意図して独自に調整したのか再確認が必要。

参考値との差がOKLab距離0.05を超える色は25色、0.10を超える色は14色。これは監査上の比較用の区切りで、合否基準ではない。グラファイトのような低彩度の色は、小さな色差でも暖色・寒色の印象が変わる。

改善する場合の順序

  1. 色名の基準を決め、各色に出典と独自調整の有無を記録する。
  2. グラファイト・チャコール・ディムグレーを優先して見本を確認し、修正した色味が白を混ぜても維持されるか検査する。
  3. 見本のHEX、仮想顔料、結果の色名辞書を一緒に点検する。暖色顔料を追加する場合も、既存補正との二重適用を避ける。
  4. UIカテゴリーと有彩色の扱いを分離し、低彩度の色味をどの程度混色に反映するか決める。
  5. 外部参考値との照合、灰色の暖色・寒色、結果名の矛盾候補を既存の自己整合性テストへ追加する。

参考：洋色大辞典、W3C CSS Color 4 Named Colors。数値記録：color-model-audit.json / color-reference-audit.json。
